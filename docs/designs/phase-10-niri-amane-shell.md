## Problem Statement

Dotfield is a declarative Linux ricing engine and dotfile compiler built in Rust adhering to the principle: *"Store logical choices, not duplicated config."*

In Niri (a scrollable-tiling Wayland compositor), status bar support was temporarily bridged using `i3bar-river` spawning `i3status-rs` via standard i3bar JSON streaming. While functional, this multi-process architecture is an awkward retrofit:
1. **Protocol Fragility**: Unknown configuration keys (e.g. `start_hidden` in `i3bar-river` v1.1.0-1) break configuration parsing and cause silent fallback to empty bars.
2. **Impedance Mismatch with Niri**: Niri's UI model is an infinite horizontal ribbon of tiled columns, not a discrete row of numbered i3/Sway tags. A standard i3bar cannot visualize horizontal scroll positions, active column focus, or Niri workspace layout.
3. **Redundant Process Tree**: Running a layer-shell host (`i3bar-river`), a shell wrapper (`sh -c`), and a status generator (`i3status-rs`) introduces IPC latency, extra memory overhead, and uncoordinated reload mechanics.

The user's direct requirement for Phase 10: *"for premise 3 if amane can replace i3bar or i3status then replace it"*. Dotfield will replace the multi-process bridge with a native, pure Rust desktop shell built on **Amane** (`MystiaFin/amane`).

## What Makes This Cool

- **Vulkan / wgpu Hardware Rendering**: Direct GPU-accelerated rendering on Wayland `wlr-layer-shell` without any GTK, Qt, or web runtime dependencies.
- **Ultra-Lightweight Footprint**: Consumes <15MB of RAM with sub-millisecond frame times and zero CPU wakeups when idle.
- **Spatial "Workspace Radar"**: Visualizes Niri's horizontal workspace strip and active column layout in real time through direct connection to `$NIRI_SOCKET`.
- **Pure Rust Workspace Unity**: Brings the desktop shell directly into the Dotfield Cargo workspace alongside `dotfield-core`, `dotfield-cli`, and `dotfieldd`, sharing type definitions and CI verification.

## Constraints

- **Declarative User Surface**: End users must never be forced to write or compile Rust code to configure their desktop. Ricing choices remain declarative in `profiles/*.toml` (`[bar]`, `[theme]`, `[apps]`).
- **Controlled Chaos Palette Compliance**: Strict enforcement of Dotfield's design tokens:
  - `Void Black`: `#0A0A0C` (Bar background)
  - `Obsidian`: `#121216` (Block container backgrounds)
  - `Graphite`: `#1C1C23` (Borders and separators)
  - `Iron`: `#34343D` (Inactive workspace markers)
  - `Crimson`: `#E63946` (Urgent workspace / alert state)
  - `Amber`: `#FFB000` (Active workspace / primary accents)
  - `Bone`: `#E8E6E3` (Foreground text and active labels)
- **Atomic Rollout & Selective Reload**: Dotfield compiles shell manifests to `.dotfield/staging/generation-N/shell.toml`. Deployments are atomic symlink swaps, and reloads occur without restarting Niri or flickering the display.
- **Strict Quality Gates**: Zero-warning policy under `cargo clippy --all-targets -- -D warnings`, `cargo fmt -- --check`, `cargo test`, `gitleaks`, and `semgrep`.

## Premises

1. **Native IPC Over Retrofitting**: Niri's dynamic scrollable workspace model requires direct event socket consumption (`$NIRI_SOCKET`), not generic i3bar JSON bridges.
2. **Design System Invariance**: Controlled Chaos typography and color tokens must govern all shell visual rendering.
3. **Complete Replacement**: Amane replaces both `i3bar-river` and `i3status-rs` for Niri in Dotfield.
4. **Stable Manifest Boundary**: Dotfield generates a stable versioned manifest; upstream Amane framework API changes must never leak to user profiles.

## Cross-Model Perspective (Codex Cold Read)

- **Coolest Version**: A scroll-aware "workspace radar" shell that renders Niri's infinite horizontal plane as interactive, spatial objects with window focus, groups, and urgency.
- **Key Insight**: The user's strongest motivation is eliminating retrofit plumbing: *"if amane can replace i3bar or i3status then replace it"*.
- **50/50 Split**: `MystiaFin/suzuha` provides ~50% of the architecture (Amane layer-shell + Niri socket IPC). The remaining 50% is Dotfield-specific: declarative manifest generation, Controlled Chaos token injection, atomic deployment, and rollback.
- **Architectural Risk (High)**: Amane is a framework, not a static-config daemon. Dotfield must own the shell binary (`dotfield-shell`) over a stable manifest rather than having users compile Rust.
- **Recommendation**: Build a narrow, Dotfield-owned Amane shell over a versioned manifest.

## Approaches Considered

### Approach A: Minimal Viable — Standalone Shell Binary with Compiled TOML Manifest
- **Summary**: A standalone binary with a fixed widget layout (Niri workspaces, window title, clock, battery, audio). Dotfield compiles `[bar]` and `[theme]` profile keys into `~/.config/dotfield/amane-shell.toml`, autostarted by Niri.
- **Effort**: Medium (M) | **Risk**: Low
- **Pros**: Fastest to green, static widget set, simple SIGHUP reload.
- **Cons**: Fixed widget ordering in code, minimal extensibility.
- **Reuses**: Leverages `MystiaFin/suzuha` patterns and `dotfield-core` TOML compilation.

### Approach B: Ideal Architecture — First-Class `dotfield-shell` Workspace Crate with Spatial Workspace Radar
- **Summary**: Add `crates/dotfield-shell` directly into the Dotfield Cargo workspace. It imports `dotfield-core` profile definitions and Amane, rendering a spatial workspace radar matching Niri's infinite ribbon. Dotfield generates versioned staging manifests (`.dotfield/staging/generation-N/shell.toml`) with strict Controlled Chaos tokens, supporting atomic rollout and zero-flicker reload.
- **Effort**: Large (L) | **Risk**: Medium
- **Pros**: First-class citizen in `cargo check`/`clippy`, purpose-built for Niri, shared data models, full rollback integration.
- **Cons**: Adds wgpu/Wayland dependencies to workspace build.
- **Reuses**: Integrates directly with `dotfield-core::profile::Profile`, palette constants, and `dotfield-cli` selective reload engine.

### Approach C: Creative / Lateral — Unified Desktop Shell & Hardware Daemon inside `dotfieldd`
- **Summary**: Merge the Amane shell directly into `crates/dotfieldd`, creating a single unified daemon managing the top bar, on-screen displays (volume/brightness overlays), and hardware AC/battery events.
- **Effort**: Extra Large (XL) | **Risk**: High
- **Pros**: Single process for bar, OSD, and events; zero IPC latency.
- **Cons**: High blast radius (render crash kills the daemon), significant scope creep.
- **Reuses**: Extends `crates/dotfieldd` event loops.

## Recommended Approach

**Adopt Approach B: First-Class `dotfield-shell` Workspace Crate.**

The user explicitly approved Approach B.

## Open Questions

1. **Multi-Monitor Strategy**: Should `dotfield-shell` spawn an identical layer-shell bar on every connected Wayland output, or bind specifically to the focused/primary monitor?
   *Proposed default*: Spawn an independent bar surface per active output, tracking per-output workspace state.
2. **Interactive Workspace Clicking**: Should clicking a workspace tile dispatch an immediate Niri focus action (`niri msg action focus-workspace <id>`)?
   *Proposed default*: Yes, implement pointer click handlers on workspace radar tiles.

## Success Criteria

1. `cargo check --workspace`, `cargo test`, and `cargo clippy --all-targets -- -D warnings` pass with zero errors and zero warnings.
2. Running `dotfield apply minimal` generates `.dotfield/staging/generation-N/shell.toml` with valid Controlled Chaos color tokens.
3. Niri autostarts `dotfield-shell` cleanly on startup; top bar appears with height 32px.
4. Moving across workspaces in Niri dynamically updates the workspace radar in <1ms without stutter.
5. Overall shell memory usage stays below 20MB RSS.

## Distribution Plan

- `dotfield-shell` is built directly as part of the `dotfield` workspace:
  ```bash
  cargo build --release
  ```
- Binaries (`dotfield`, `dotfield-cli`, `dotfield-shell`, `dotfieldd`) are installed via standard Cargo or packaging channels to `~/.cargo/bin` or `/usr/local/bin`.
